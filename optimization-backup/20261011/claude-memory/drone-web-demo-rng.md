2026-09-06. Browser build of the t387 demo (64x2, 15 s) had race OOB 0.46 vs native 0.00 with identical weights, config and loop.
Root cause: the drone env draws everything through `rand_r` (dronelib.h `rndf`); emscripten's libc is musl, whose `rand_r` is a different algorithm from glibc's, so the browser gets a different random stream. Both streams are statistically uniform and uncorrelated (measured), so this only matters because `race_env_reset` generates the 10-ring track ONCE per env in `puf_reset` and never again: one env = one track for its entire life. Native musl-shim eval reproduced the browser numbers exactly (OOB 0.46, 9.3 rings), and a glibc-`rand_r` shim in the wasm build reproduced native to the digit (0.00 OOB, 14.1 rings).
Per-track heavy tail (t387, native, race forced, 72 glibc seeds, 1000–1500 eps each): seed 6 OOB 0.46, seed 300 0.11, seed 310 0.06, seed 4 0.05, seed 320 0.04; ~93% of tracks under 1%; mean ≈1.1%. The trainer seeds env i with rng=i (pufferl.cu:1005) with NO rank offset, so all 8 GPU processes train on the same N tracks and the inline final eval averages over those same tracks — a 0.6% eval OOB can hide a 46% killer track, and a single-env demo is a track lottery.
Fix shipped in worktree $S/wt_97416d02 only (not committed): `ocean/drone/dronelib.h` defines glibc's `rand_r` under `__EMSCRIPTEN__` so web streams match the trainer; page build/web/drone_387 is that build (drone_387_musl keeps the crashing one). `src/puffercpu.c` there also has PUF_SEED env override + TRACE/WEB_LOG diagnostics (not for shipping).
