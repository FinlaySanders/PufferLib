MLP-Mixer nethack encoder shipped 2026-07-06 in src/ocean.cu (NHM_* constants/kernels), selected via env var NETHACK_ENCODER=mixer (default = conv). Arch: embed d=16 → 3x3 non-overlap patch stem → 64ch tokens (49) → 1 norm-free mixer block (token-mix hid 64 on token-dim PADDED to 64, channel-mix hid 96) → flatten ‖ blstats → proj. tok_w2/ch_w2 zero-init (identity residual at init). 793K params vs conv 676K. Gradient-checked by tests/test_nethack_mixer.py (+ test_nethack_mixer_cuda.cu). See [[nethack-training-profile]].

RESULT: mixer correct but SLOWER than the cudnn conv encoder — clean SPS 150K vs 216K; train phase 1125 vs 715 ms/epoch (encoder 654 vs 296). Root cause is BANDWIDTH not flops: token/hidden activations (50-100MB each at minibatch 8192) × unfused elementwise passes (bias_relu, relu_backward, bias-grad, transposes) ≈ 2GB+/iter. Next lever if score justifies it: cublasLt epilogues (RELU_BIAS fwd, DRELU_BGRAD bwd); even then expect ~parity with conv, not a win.

NETHACK_ENCODER=patch (added same day): the mixer with the mixer block gated off (use_mixer flag on weights struct; stem → concat directly) = embed→3x3-patch-linear→flatten‖blstats→proj. UPDATE 2026-07-07: stem now computed through a fused per-glyph table (T = E @ stem_w', 5977x576; no gathered-embedding buffer, dT-table backward like the conv path) — patch is now the FASTEST encoder: encoder 127 vs conv 227 ms/epoch, SPS 328K vs 275K; see [[nethack-encoder-perf]]. NHM_CONCAT padded 3245→3248 for tensor-core proj GEMMs — old patch/mixer checkpoints incompatible. All variants gradient-checked.

SCORE A/B RESOLVED (2026-07-07 runs): **patch BEATS conv by ~200 score** and set the SOTA run (score 918, depth 5.73, 259M steps, 21-action config — prior best 4.5 depth @ 80M). NETHACK_ENCODER=minpatch (added after: patch stem + learned linear pool of 49 tokens → NHMP_K=16 spatial tokens, flatten 1024, concat padded 1136) only MATCHES conv's score — the full 49-token flatten matters. Patch = the encoder of choice: fastest AND best score. Note the patch speed advantage shrinks late in runs because env c_step grows (longer/deeper episodes) and dilutes train-side wins — see [[nethack-encoder-perf]].

NETHACK_ENCODER=cellflat (added 2026-07-07): no stem at all — raw per-cell embeddings straight into the projection (flatten 441x16=7056, concat 7168, proj 128x7168=918K params). Gradchecked (4th variant in test_nethack_mixer.py, mode 3). SPEED PARITY with patch (encoder 124 vs 127 ms/epoch), NOT faster: deleting the stem saves ~140µs/iter but the 2.2x wider flatten costs it back (115MB gather write into concat + wider proj GEMM traffic + nhcf_embed_scatter 296µs ≈ patch's dT scatter). SCORE RESULT (full run): **eventually MATCHED conv** (was ~half of patch's score at 1/3 in — much slower learner, caught up to the conv plateau by run end; still -200 vs patch). Refined score law: there is a "conv plateau" many arches reach (conv, minpatch, cellflat — wildly different mechanisms, same level); only patch's wide NONLINEAR position-keyed layer (3136 relu stem units) has broken above it. The nonlinear stem buys the +200 AND much faster learning, but isn't needed to reach baseline. Evidence-backed score knob = widen NHM_C (64→96/128, ~+10% train time per step); embed rank d 16→48 nearly-free complementary knob. GOTCHA: profile_table.py encoder pattern needed "nhcf_" added (kernels landed in other-misc, encoder looked 68ms when truly 124).

SPS IS ENDOGENOUS TO SCORE — never compare arch speed by run SPS: better policies survive longer/go deeper and env c_step cost scales with agent competence, so a better encoder lowers its own wall-clock SPS (cellflat's "highest SPS" was largely its weak agents dying on cheap shallow levels, plus a real-but-smaller mechanical factor: patch rebuilds the 6.9MB glyph table EVERY rollout forward call at rollout batch ~200 where it dominates — fix: build table once per epoch post-muon-step, weights-side, rollouts read it). Fair speed metrics: train-phase ms/epoch (policy-independent) or matched-checkpoint env cost. Corollary: the better agents get, the more env-side optimization matters relative to encoder speed.

C/D SWEEP RESULTS (2026-07-07): D=48 MATCHES baseline (identity rank 16 sufficient — keep D=16, fewer params). C=96 does WORSE than C=64 at fixed 259M steps. Patch C=64/D=16 sits at a local optimum in both probed directions — the width-scaling story saturates at 64 channels. Leading interpretation: the binding constraint moved DOWNSTREAM to the hidden=128 readout/recurrent state (3136→128 already discards 96%; 4704→128 adds params/optimization noise with no added output expressivity). Caveat: fixed-step budget — check whether C=96's curve was still climbing (bigger nets learn slower; cf. cellflat catching conv late). Next evidence-backed run: hidden 128→256 at C=64/D=16 (July-6 profiling: mingru latency-bound, wider hidden ~cheap), then re-test C=96 at hidden=256 if it helps. Cheap speed option: C=48 run — if it matches C=64, encoder gets faster at par score.

RUNTIME KNOBS + TABLE CACHE (2026-07-07, uncommitted): NETHACK_ENCODER_C / NETHACK_ENCODER_D env vars set token channels / embed dim at runtime for patch+cellflat (multiples of 8; mixer/minpatch guarded to 64/16). Kernels take C/D args; dT scatter uses dynamic smem (7*9C+C floats, 32.7KB @ C=128); scatter grids adjusted so stride%C==0 (register bias trick). Fused table now WEIGHTS-SIDE (cudaMalloc in create_weights): train forwards rebuild per minibatch (a->is_train flag set by reg_train/reg_rollout), rollouts just read it — new Encoder.post_step hook (models.cu) refreshes it once per epoch (end of train_impl, pufferlib.cu) and after bindings.cu load_weights; init_weights builds it for the pre-training rollouts. Gradcheck covers 7 configs incl. (C96,D48),(C128,D32). Measured: patch C64/D16 SPS 322K encoder 135ms; C96/D48 SPS 294K encoder 222ms train +16%, params 1.2M, learns fine (perf 10.0 @ 2M).

Hard-won CUDA lessons encoded:
- Odd inner dims (tokens=49) disqualify TC kernels via 16B alignment → pad to 64 (zero-fill pad in the transpose; pad weights get zero grads, mathematically inert).
- Tiny-output/huge-K wgrads (e.g. 96x64, K=524288) run ~near-serial (3.5-7.7ms!) under cublasGemmEx DEFAULT — no split-K for small N. Fix: puf_mm_tn_splitk in kernels.cu using cublasLt heuristic + 64MB workspace (→ 72-212µs). Needed -lcublasLt in build.sh AND both test nvcc commands.
- Generic bias_grad_kernel (block-per-column, strided reads) is ~10x slow at 400K+ rows → nhm_bias_grad_kernel (coalesced grid-stride + smem + fp32 global atomics), still costs a full tensor re-read per bias.
- FD gradient tests on deep-relu stacks have a near-kink noise tail below any kink threshold → use MEDIAN rel err (<1e-2) + max<0.15 instead of pure max; bias params are the noisiest (one bias shifts a whole relu unit across all rows).
- profile_table.py encoder patterns must include nhm_ (nh_ prefix match misses it in python; SQL LIKE 'nh_%' matches since _ is a wildcard).
